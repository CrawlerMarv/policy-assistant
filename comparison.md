I evaluated the three approaches on 20 test questions against the 98-policy database: seven use the policy's own wording, seven are paraphrased, one asks for a detail the matching policy does not state (the number of sick days), and five ask about something no policy covers. The rules-based BM25 search answered every directly worded question correctly in under a millisecond and without any tokens, but it found the right policy for only 2 of the 7 paraphrased questions, because it can only match words that literally appear in a policy ("jeans" never leads to the Dress Code Policy). It also gave the only unsupported answer in the test: asked about a home-internet allowance, it returned the Internet Usage Policy, which says nothing about one. Both language-model approaches used Gemini 3.5 Flash-Lite with the same instruction to answer only from the supplied policies; both identified the right policy for all 15 covered questions, declined all 5 uncovered ones, and produced no answer flagged as unsupported.

Accuracy therefore does not separate the two language-model approaches, but cost and scalability do. Without a vector index, every request carries the whole database: 2,128 tokens and 0.91 s per question on average. With the vector index, only the three most similar policies are sent, which cuts this to 290 tokens (86 % fewer) and 0.78 s. Because the full-context prompt grows with every policy added while the retrieval prompt stays roughly constant, the gap widens as the handbook grows, so I prefer the language model with a vector index, which is also what the Slack bot uses. Its main risk is retrieval: if the right policy is not among the three candidates, the model cannot find it. The small test set did not trigger this, and the unsupported-answer checks cannot detect invented claims that contain no figures, so the results are indicative rather than conclusive.
